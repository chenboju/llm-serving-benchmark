# 00 — 測試目標與範圍（DGX Spark）

> 先讀這份。環境建立見 [01-環境建立-dgx-spark.md](01-環境建立-dgx-spark.md)，
> 驗收關卡見 [02-驗證清單.md](02-驗證清單.md)，報告格式見 [03-報告範本.md](03-報告範本.md)。

## 一、這台機器的定位

| 項目 | 內容 |
|---|---|
| 硬體 | NVIDIA GB10 Grace Blackwell（DGX Spark 單節點） |
| OS / 架構 | NVIDIA DGX OS，**ARM64 (aarch64)** |
| 記憶體 | 128 GB 統一記憶體（CPU 與 GPU 共用） |
| Runtime | **llama.cpp 與 vLLM 兩者都跑** |
| 本機計畫 | `gpt-oss-20b-dataset-v1-dgx` |
| 與參考機的關係 | 完整複製 RTX 4090 的 A/B 對照，只換硬體 |

這台跟 AI Max+ 395 那台的差別很大，不要套用同一套預期：

| 面向 | DGX Spark | AI Max+ 395 |
|---|---|---|
| vLLM | **可以跑** | 不能跑 |
| 對照設計 | 完整 A/B（雙 backend） | 單邊（僅 llama.cpp） |
| OS | Linux | Windows |
| GPU 遙測 | nvidia-smi + pynvml，與 4090 完全相同 | amd-smi / 可能沒有 |
| harness 改動 | 很小 | 較大 |

## 二、為什麼這台特別有價值

跑完之後會形成一個 **2×2 設計**：

| | llama.cpp | vLLM |
|---|---|---|
| **RTX 4090**（24 GB GDDR6X，x86_64） | 已跑 | 已跑 |
| **DGX Spark**（128 GB 統一記憶體，aarch64） | 待跑 | 待跑 |

有了這四格，才能把「硬體差異」與「runtime 差異」分離開來。AI Max+ 395 只有左欄，
做不到這件事。這是 DGX Spark 這一輪最主要的產出。

## 三、本機要回答的問題

| 編號 | 問題 | 對應 suite |
|---|---|---|
| Q1 | GB10 上 llama.cpp 與 vLLM 的相對關係，是否與 4090 上一致？ | 全部 comparison cells |
| Q2 | 記憶體頻寬受限的平台上，vLLM 的高併發優勢還在不在？ | sharegpt_closed C8/16、vllm_stress C32/64 |
| Q3 | 128 GB 統一記憶體能不能撐住 4090 撐不住的長上下文格？ | ruler_performance 60K、rag 16K C8 |
| Q4 | prefix cache 的改善幅度是否跨硬體一致？ | prefix（另跑） |
| Q5 | vLLM 的 34 個壓力 cell 在這台是否可完整執行？ | vllm_stress |

Q2 是重點。4090 的舊版基線顯示 vLLM 在 C16 有 2.48× 的 decode 優勢，那是在
1 TB/s 等級頻寬的離散顯卡上。GB10 的統一記憶體頻寬低一個量級，continuous batching
的收益能不能維持，是這台機器要驗證的核心假設，**不要事先假定結論**。

## 四、不做什麼

| 不做 | 原因 |
|---|---|
| GPT-OSS-120B 單節點 / 雙節點 Ray TP | 另一條 track。本資料夾的 matrix、tokenizer、ctx 全部綁定 20B，換模型要換整套資料集 |
| 跨節點 Tensor Parallel | 同上，屬於 `vllm-120b-dual-dgx` profile |
| 重新產生 datasets | 必須沿用參考機產生的檔案 |
| tokens/Wh | 無一致的插座功率計 |

120B 與雙節點是真實且重要的題目，但它們是**系統 scaling** 的展示，不是這份
20B 跨硬體對照的一部分。混在同一場 campaign 會讓兩邊都說不清楚。

## 五、比較邊界

| 比較 | 是否可直接比較 | 條件 |
|---|---|---|
| 本機 llama.cpp vs 本機 vLLM | **可以** | 同機、同資料集、同時段，這是主要的 A/B |
| 本機 llama.cpp vs 4090 llama.cpp | **可以** | 同 GGUF、同 b8407 tag、同資料集 |
| 本機 vLLM vs 4090 vLLM | **有條件** | 只在兩邊 vLLM 版本相容時；ARM64 容器與 x86_64 容器版本常不同步 |
| 本機 vs AI Max+ 395 | 僅 llama.cpp 那一側 | 且要標註 CUDA vs ROCm/Vulkan |

無法消除的差異，報告必須列出：

| 差異 | 影響 |
|---|---|
| aarch64 vs x86_64 | llama.cpp 是不同架構的 build，即使 tag 相同 |
| GB10 vs Ada | CUDA compute capability 不同，kernel 選擇可能不同 |
| 統一記憶體 vs 離散 VRAM | `--gpu-memory-utilization` 的實際意義不同 |
| vLLM 容器版本 | ARM64 映像與 4090 用的映像可能不同版 |

## 六、狀態用詞

與參考機相同，四種狀態必須分開：

| 狀態 | 判定 |
|---|---|
| 資料已驗證 | `validate_prepared.py` |
| Cell 有效（valid） | ≥3 valid repeats、exit 0、無 OOM、error ≤ 1% |
| Cell 通過 SLO | Good Request Fraction ≥ 95% |
| 矩陣已完成 | 該 scope 全部 cell 皆 valid |

## 七、預估工時

profiling 時間由 `duration_seconds` 固定，**與機器快慢無關**——慢的機器只是在同樣的
300 秒內完成較少 request，不會跑比較久。

| 範圍 | Backend-cells | 純 profiling 時數 |
|---|---:|---:|
| llama.cpp comparison（含 prefix） | 45 | 11.25 |
| vLLM comparison（含 prefix） | 45 | 11.25 |
| vLLM stress | 34 | 8.5 |
| 合計 | 124 | **31** |

實際牆鐘時間會明顯更長（warmup、idle gate、模型載入、容器啟停、不穩定重跑）。
按 4090 的經驗抓 **1.4–1.6 倍**，約 45–50 小時。建議分多天執行，每次一個 suite，
用同一個 `CAMPAIGN_ID` 累積。

## 九、尚未移植的部分

本資料夾只涵蓋 **dataset campaign**（`scripts/dataset-tests/`）。參考機上還有另一層
**微基準 suite** 沒有移植過來：

| 未移植的 suite | 位置（參考機） | 產出 | 依賴 |
|---|---|---|---|
| llama.cpp 微基準 | `scripts/llama-cpp-tests/` | startup、context scaling、concurrency scaling、prefix cache | llama-benchy、`nvidia-smi` |
| vLLM 微基準 | `scripts/vllm/` | 同上，vLLM 版 | 同上 |

參考機報告第七節的表格（context scaling 的 prefill tok/s、concurrency scaling 的
decode tok/s、prefix cache 降幅）都是這一層產出的。**本機目前無法重現那些表格。**

好消息是這台移植成本比 AMD 那台低很多：兩個目錄約 2,900 行 bash，深度耦合
`nvidia-smi` 與 Docker——而這台**兩者都有**，且是 Linux。理論上大部分腳本可以近乎
原樣執行，只需確認路徑與 aarch64 相關假設。llama-benchy 本身是純 Python client，
完全可攜。

| 選項 | 說明 |
|---|---|
| 不移植 | 只做 dataset campaign，報告第七節留空並註明 |
| 原樣帶過來試跑 | 這台最有機會直接可用；先在單一 suite 上驗證 |
| 手動跑 llama-benchy | 直接對端點跑，自行記錄，沒有自動化存證 |

這是**尚未決定**的範圍問題，不是遺漏。動手前先確認要哪一個。

## 十、之後換模型（20B → 120B）

這台是唯一有能力跑 GPT-OSS-120B 的機器（128 GB 統一記憶體，且 `vllm-120b-single-dgx`
與 `vllm-120b-dual-dgx` profile 就是為它定義的），所以換模型的問題在這裡最實際。

| 項目 | 是否需要更換 | 說明 |
|---|---|---|
| GGUF / HF snapshot | 是 | |
| `backends.*.model`、`deployment` | 是 | |
| `llama_server.ctx_size`、matrix 的 bucket_tokens | 視模型 context 上限 | `validate_cells()` 有 `bucket + output < 65536` 的安全邊界斷言 |
| vLLM 容器 | 是 | 120B 需要不同的記憶體與 TP 設定 |
| **prepared datasets** | **需先確認** | 關鍵，見下 |

**資料集是 tokenizer 相依的**。`prepare_datasets.py` 依 tokenizer 把 RAG / RULER /
prefix 的 prompt 修剪到目標 bucket（±5%），`validate_prepared.py` 也用 tokenizer
算出的 `actual_input_tokens` 驗證。所以：

1. 先比對 20B 與 120B 的 tokenizer 是否**位元相同**（比 `tokenizer.json` 的 SHA-256）
2. 相同 → 現有 prepared datasets 可直接沿用，換模型只需改 config 與模型檔
3. 不同 → 必須用新 tokenizer 重新產生整套 prepared datasets，新舊結果不可互相比較，
   等於開一個新的正式計畫

換模型前先做這個比對，不要假設兩個模型的 tokenizer 一樣。

另外提醒：120B 的單節點 / 雙節點 Ray TP 是**系統 scaling** 的題目，與 20B 的跨硬體
對照是兩件事。即使 tokenizer 相同、資料集可沿用，也應該用不同的 `CAMPAIGN_ID`
分開存放，不要混進 20B 那場。
